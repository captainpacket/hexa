# ADR-2611050000: Template-Driven Telemetry Rendering

## Status
Proposed

## Context
The introduction of the `SemanticCompressor` in `hexa-infer` allows the system to handle massive conversation histories by recursively summarizing older turns. While this is technically successful, the operator has no visibility into the "Context Health"—they don't know if the agent is currently operating on a highly compressed history or if the compression ratio is degrading.

Currently, `InferenceResponse` in `hexa-core` has been updated to include a `telemetry` map, but this data is not surfaced in the `hexa-cli` UI.

## Decision
We will implement a template-driven telemetry rendering system in `hexa-cli` to surface these metrics in the status line during `hexa run` and `hexa loop`.

1. **Telemetry Asset**: Define a new asset `hexa-cli/assets/telemetry.json` that maps telemetry keys to visual representations (an icon and a label each).
2. **Formatter Logic**: Implement a `telemetry_badge` function in `hexa-cli/src/fmt.rs` that consumes the `telemetry` map and the asset to produce a formatted string.
3. **Status Line Integration**: Update the primary execution loop in `hexa-cli` to append these badges to the active status line.

The API, all in `hexa-cli/src/fmt.rs` (the tests call it as `hexa_cli::fmt::…`):

```rust
/// How one telemetry key is shown: `{icon} {label}: {value}`.
pub struct TelemetryEntry { pub icon: String, pub label: String }

/// The asset, keyed by telemetry key.
pub struct TelemetryAsset { /* private */ }
impl TelemetryAsset {
    /// Parse the text of `telemetry.json`. Never fails: malformed text gives an
    /// empty asset and a warning on stderr, so the binary starts regardless.
    pub fn parse(text: &str) -> TelemetryAsset;
    pub fn get(&self, key: &str) -> Option<&TelemetryEntry>;
}

/// One `{icon} {label}: {value}` per key the asset knows, in key order, joined
/// by a single space. A key the asset does not know is left out. Plain text:
/// the caller styles it. Empty when nothing is shown.
pub fn telemetry_badge(telemetry: &std::collections::HashMap<String, String>, asset: &TelemetryAsset) -> String;

/// `line`, then a space and `badge`; `line` unchanged when `badge` is empty, so
/// a quiet loop gains no trailing whitespace.
pub fn append_telemetry(line: &str, badge: &str) -> String;
```

An entry of `telemetry.json` has an `icon` and a `label`; the value is shown as the run reports it.

## Amendment (2026-11-16): where the telemetry comes from, and what compresses

The rendering above is built. The data behind it was not coherent, and this
records what the compression actually does now.

**Two layers, one budget, one owner.** The ReAct loop (`hexa-exec`,
`direct_react` through `compress::prepare_step`) compresses mechanically every
step — each observation capped head-and-tail, a rolling window of recent ones —
and makes one cheap summarization call only when the result is still over the
budget. `hexa_infer::complete::complete_raw_with` then used to compress again,
at its own 4 000-token trigger, with `SemanticCompressor` down to 2 000 tokens
on a model literally named `"t1"`: it undid the loop's sizing, could summarize
away file text the model had to quote for `replace_string`, and added paid calls
on most steps. Now:

- The budget is one constant, `hexa_infer::ports::COMPRESSION_THRESHOLD_TOKENS`
  (12 000 estimated tokens, chars / 4). The loop's `MAX_CTX_TOKENS` is
  `compress::LOOP_BUDGET_TOKENS`, which is that constant.
  `complete_raw_with` never compresses at or below
  `PromptCompressor::threshold_tokens`, which is never below it;
  `.hexa/project.json → inference.compression.threshold_tokens` may raise it,
  and a lower value is raised to it. The estimate counts every block — tool
  results and tool inputs included; it used to count text blocks only.
- A caller that compressed says so in the request: `"compression":
  {"already_compressed": true, "layer", "original_tokens", "compressed_tokens",
  "summarization_calls"}` (`ports::COMPRESSION_KEY`). `complete_raw_with` then
  does not compress, and reports the caller's figures. The loop always sends it,
  so a loop step costs at most one summarization call, the loop's own.
- `SemanticCompressor` (kept) never summarizes what must stay verbatim: the
  system prompt (not a message), the most recent plain user turn, the last
  `keep_recent_tool_results` tool results (4; `inference.compression.
  keep_recent_tool_results`), every result of a file-read tool (`repo_read`,
  `read_file`), and the last two messages. A kept result keeps its `tool_use`
  and the reverse. The rest becomes one summary, by recursive rounds of up to
  four chunks, stopping at the budget, at a round that does not shrink, or at
  `max_summarization_calls` (8); what is still over is capped.
- Its cheap model is tier `t1` resolved through the tier configuration
  (`inference.tier_models.t1`). None configured, or a failed summarization:
  the unpinned turns are capped head-and-tail instead, no call is made with an
  unresolved name, and `compression_note` says why. A compressor error never
  fails the user's call.

**The telemetry keys** in a `complete_raw` reply: `compression_layer`
(`none`, `semantic`, `mechanical`, or the caller's — the loop sends
`mechanical` or `mechanical+summary`), `original_tokens`, `compressed_tokens`,
`summarization_calls`, and when something was compressed `compression_ratio`
and `tokens_saved`; `compression_note` when a layer fell back.

**What does not yet reach the badge.** `hexa loop`'s status line reads the
`telemetry` map from the loop state (`.hexa/loop.json`). Nothing writes that
map: `direct_react` reads only `content` from the reply. So the badge renders
correctly from data it never receives, and shows nothing during a real run.
Carrying the last step's telemetry into the loop state is the remaining work.

**Gate:** `cargo test -p hexa-infer --lib -- compression_tests semantic_compressor
compressor_config_tests` and `cargo test -p hexa-exec --lib -- compress::tests`,
with `cargo test -p hexa-cli --test adr_2611050000_spec` for the rendering.

## Consequences
- **Positive**: Operators gain real-time visibility into the efficiency of the semantic compressor.
- **Positive**: UI formatting is decoupled from the binary, allowing for rapid iteration and project-specific customization via assets.
- **Negative**: Adds a small overhead to load the telemetry asset on startup.
- **Neutral**: Introduces a dependency on the `telemetry` map in the `InferenceResponse` contract.

## Gate

`cargo test -p hexa-cli --test adr_2611050000_spec`: the sealed tests of the spec's eight scenarios: the
asset parses and a malformed one yields an empty mapping, the badge renders full, partial, empty and
unknown-key telemetry, and the status line gains the badge without trailing whitespace.
